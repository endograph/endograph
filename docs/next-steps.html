Endograph — next steps

From a build-and-deploy agent to a general, evolutionary, embedded agent framework. 2026-08-30.

Where it stands

An agent is a directory: a charter (prose mandate), a grant (money, model, tools), an inbox, a playbook the agent writes itself, and a frame log. The loop is sense → rule → act, else judge → act → reply → record. Rules are strict scripts: exit 0 handled, 64 refused, 75 in progress, anything else falls to the model with the output in hand. Capex is lazy (every N judged requests) and compacts history. The whole thing runs as a launchd user agent.

Endofrog proved the shape in one day: it learned its procedures from the repo, distilled ordinary deploys into a zero-token rule, re-learned when the repo moved, and fixed its own relaunch flake when asked.

What held up

  • Plumbing vs. charter. Nothing domain-specific ever needed to enter endograph; every gap was a missing generic tool.
  • Trust the model for noticing; give it moments and tools. Memory-based noticing works when history is compacted and capex is framed as "the default outcome is nothing".
  • Strict scripts + judgment fallback is the right split: the boring path is free, the exception path is still safe.
  • Every hand-fix was a missing tool. try_rule, playbook frames, sh -n, the explained matcher miss — each came from watching the agent get something wrong.

Next steps

1. Close the evolution loop highest leverage

Today the agent can write rules; it cannot see how they perform, cannot undo a bad rewrite, and only notices problems when a request fails.

  • Experience as a git repo. Make src/ its own repository; every agent write is a commit. Gives endo playbook log|diff|revert for free and a reviewable trail of the agent changing itself.
  • Rule statistics projected into context. Fired / failed / refused / superseded-by-judgment counts and last-fired time per rule, in the world model. Noticing stays memory-based; the memory just has numbers in it.
  • Regret signal. When judgment overrides a rule's refusal or repairs what a rule did, tag the rule. Two regrets → the next capex session is told about it.
  • Shadow rules. A new rule can run alongside judgment for a few incidents (ENDO_TRY) and compare outcomes before it takes over.

2. Watch, don't just answer the "embedded" half

Endofrog only reacts to the inbox. An infrastructure agent should also notice: stout woke up, HEAD moved, Froggy crashed.

  • Playbook sensors. kind = "sensor": a script polled every N seconds; a change in its output is a drift. The model can write its own sensors — that is what makes the agent evolutionary rather than just configurable.
  • Jobs as first-class. Exit 75 starts background work but nothing sees it: a jobs entry in the world model (pid, request, started, log tail), endo jobs, and a job.finished drift so rules or the model can react and reply.
  • Retry on schedule without a scheduler. "Stout is asleep" should become a sensor that fires when it wakes, not a rule that sleeps.

3. Peers agent-to-agent

  • A registry (~/.endo/agents, or foxnet's) so endo send endofrog … works by name from anywhere.
  • Remote inboxes. The inbox is a directory; endo send host:path over ssh is a one-liner. Keeps the single-writer frame log.
  • Delegation. A delegate tool: send a request to a peer and wait, inside an activation. Endofrog asks a stout-supervisor to wake stout; a dev-supervisor asks a deploy agent to ship.
  • Escalations that find the owner. Fire-and-forget only works if failures arrive somewhere: a notification channel in the grant (herdr, macOS notification, a file the owner's agent watches).

4. Cost

  • Elide old tool output between compactions. Most of the 40–100k input tokens per activation is bash output from earlier activations. Keep the last K activations verbatim, older ones as one line each. Stays "all frames since compaction" — just not all their bodies.
  • Triage with a small model. Optional: a cheap model classifies a request as known-class-with-rule / needs-judgment before the big one wakes. Deterministic matching stays first.
  • Prompt caching. The charter + tools prefix is stable; mark it cacheable on providers that support it (the AI SDK executor already does for Anthropic).

5. Hardening

  • An integration harness for up: memory store, mock model, real inbox directory; the wiring bugs of today (stale spread, NaN counter, un-hydratable snapshot) were all only caught live.
  • endo doctor: credentials resolve, launchd loaded and un-sandboxed, PATH has the toolchain, DNS works from the service.
  • Linux: systemd user units behind the same install.
  • Templates: a charter-only template distilled from endofrog next to the dev-supervisor one; endo init as a prompt-driven wizard.

6. Upstream to projector

  • Compaction as a core primitive (a frame that begins history).
  • A history projection with body elision.
  • Terminal-action values on ExecutorRunResult, and a runUntilQuiescent helper for the one-step-per-activation loop.

Questions for the owner

  • How reviewable should self-modification be — a git trail you can look at, or a step you approve? (The design says the former.)
  • One agent per domain, or can a project hold several that talk to each other?
  • Cross-machine trust: is any agent on the tailnet a peer, or only named ones?
